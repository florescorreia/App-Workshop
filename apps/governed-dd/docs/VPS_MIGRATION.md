## Cross-account ingress release design

Each tenant account owns its backend, execution, provider and ingress networks. Add the app-owned tenant bridge from infra/vps/tenant-bridge.container.template, bound only to a unique reviewed host loopback port. Its nginx config requires a control-plane client certificate signed by the dedicated control CA, uses a tenant-specific server certificate/key, and routes only governance `/api/`, Explorer, native Paperclip and optional Lab. Database/Bolt/MCP/provisioning endpoints have no bridge route. Add the bridge unit to the tenant target Requires/After membership and resource inventory (one extra VPS service, 128 MiB per enabled tenant). Analyst/runtime networks must have no route to host loopback or the bridge; target tests must prove that denial. Do not assume rootless networking establishes it automatically.

Control portal receives private `TENANT_UPSTREAMS_FILE`: an opaque-ID map with `dd`, `explorer`, `paperclip` and `lab` HTTPS endpoints ending in their bridge path prefixes. Set `TENANT_CA_FILE`, `TENANT_CLIENT_CERT_FILE`, `TENANT_CLIENT_KEY_FILE`; the client verifies each server certificate and presents the control certificate. Use Podman `host.containers.internal` only after verifying host-loopback reachability and certificate SAN; otherwise select a reviewed private Unix/host transport. No tenant gets the control client private key. Test native Authorization/cookies/websocket query strings across this transport and revoke sessions while streams run.

Set portal APP_BASE_URL to the allocated HTTPS origin (including8444), COMPONENT_DOMAIN to the reviewed DNS suffix, OIDC issuer/client redirects/logout to exact external origins. Component origin handling supports configurable domains and secure host-only cookies. Include every actual opaque Paperclip/Lab hostname in Caddy with valid DNS/TLS; wildcard DNS/certificates must be explicitly supported or issue individual certificates. Disable unmatched virtual hosts. The gateway must preserve external Host and HTTPS forwarded headers from trusted Caddy only. Update component CSP matching for the production suffix, using `wss:` rather than unrestricted websocket hosts. Keycloak identity UI has a separately scoped CSP compatible with its pinned inline bootstrap.

Build a production Keycloak image with `kc.sh build --db=postgres --health-enabled=true`, pin it, and use `start --optimized --http-enabled=true --proxy-headers=xforwarded --hostname=<https-origin>/identity` behind the private gateway. Set trusted proxy addresses and remove start-dev/bootstrap passwords from serving configuration after initialization. Export/import the verified realm through supported tooling; never overwrite an established realm during an update. Readiness checks must wait for realm discovery and DD storage/graph availability, not only process start. The renderer emits PostgreSQL healthchecks and dependency gates plus reverse shutdown ordering; complete Keycloak/portal/native readiness in the release manifest before installation.

Future release review sequence: allocate accounts/subordinate IDs and private loopback ports against current listeners; resolve image digests and export immutable release; validate rendered Quadlets with installed Podman Quadlet generator in dry-run; check target unit dependencies and stop ordering; install private env/assets/certificates with mode0700/0600 and correct rootless mapped owners; perform isolated encrypted restore; validate cgroup memory/CPU/PID limits and aggregate headroom; verify public authentication and negative cross-tenant tests; validate host Caddy before reload; then cut traffic over.
