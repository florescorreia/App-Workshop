# VAVE differential implementation

Source brief: [VAVE Tracking PRD](VAVE_Tracking_PRD.docx), supplied for this change. Its first-release requirements supersede the original IdeaFlow simplifications within VAVE programs. The user's later instruction explicitly authorizes adapting the two existing test ideas; their identities, original evidence and history remain retained.

## Accepted implementation decisions — 2026-10-15

- Extend IdeaFlow in place with a VAVE program workspace at `/vave`; retain React/nginx, FastAPI and PostgreSQL. New ideas use the existing persistent IdeaFlow ID/reference and append-only idea event log plus additive program/case records. Do not convert historic stages into financial approvals. Shared-workspace analytics cover the original ideas; program reports cover the program's benefit applications. The two metric definitions are never added together.
- Make VAVE the root landing page and main navigation. Adopt the two authorized evaluation ideas through version-checked preview/confirmation, preserving prior records under History. Keep old approvals/results outside VAVE totals; adoption begins Draft/M0. The independent bracket screening/quantification reviews do not imply functional approval, authorization, implementation or verified savings.
- Account roles remain User/Admin. Named program memberships supply Contributor, Manager, Functional reviewer, Finance reviewer, Authority, Viewer and External decision rights. Admin is the trusted application operator. Program access is explicit; external participants see only approved shared record fields, discussions and attachments. They cannot access the original shared workspace or program financial reports.
- The program creator supplies the actual client, sponsor, objective, scope, reporting horizon, currency, recognition rules, review cadence, evidence topics, approval threshold and decision team. No business program, classification, pilot target, account or dataset is created by startup/deployment. A fresh program defaults to Function/Quality/Safety evidence and can configure its topics.
- Capture requires title, proposed change and affected scope; the signed-in account supplies originator identity. Draft submission may be unassigned. M1 requires a responsible owner, next action, due date and Manager review. M2 requires complete application economics and Finance review. M3 requires functional evidence, resolution of critical risks and Functional/Finance decisions. M4 requires delivery actions and Authority approval, with additional Finance decision at the program threshold. M5 requires every selected application in production plus completed required actions. M6 requires independent verification of eligible elapsed application periods. Reviews and gate passage are explicit reasoned commands; gates are sequential. Material changes require reapproval while retaining snapshots.
- Financial review is independent of the accountable owner. Actual verification also excludes the actual recorder. Independent-review exceptions are not configured in this minimum release; operators cannot bypass this rule with Admin status.
- Actual verification also excludes the benefit application's owner. Actual evidence must belong to a defined elapsed application observation period inside the program horizon.
- Each application has a part/scope, plant, owner, baseline/proposed unit costs, usage/conversion factors, eligible annual/monthly quantities, adoption, baseline/effective dates, evidence type, native currency and fixed conversion rate. Incremental recurring costs and givebacks reduce retained recurring value; cash spend stays separate. Negative results and unknown values are supported. Reporting currency is program-specific; no automatic exchange-rate feed or accounting recognition is inferred.
- Shared overlap references identify alternatives for the same plant/volume/period. Conflicting selected applications prevent financial gate approval. Unselected alternatives, duplicates and parent financial allocations have visible exclusions. Parent initiative value is allocated to child applications. The operator must declare economic overlaps; semantic duplicate detection and automatic costing are not added.
- Implementation status is separate per application (Planned/Released/In production). Partial rollout contributes only in-production applications; the idea remains partially implemented until the whole approved scope satisfies M5. Actions, dependencies, risks, evidence and dated discussion remain in the same record.
- Attachments up to 5 MiB are stored in PostgreSQL and covered by its backups. Downloads are attachments with SHA-256 evidence; no external file service is introduced.
- Core views include register, maturity board, personal filters/views, program leadership/finance reconciliation and meeting exceptions. CSV mapping/import is previewed, additive and content-idempotent; imports create drafts, never approvals or verified actuals. Filtered register exports and printable review packs use the same authorized records.
- Structured search covers parts, suppliers and concept fields; register filters/sorts/grouping retain URL state. My VAVE work includes owned ideas, assigned actions, screening and gate review queues. Assignment, review, returned/material-change and deadline/escalation notices are in-app; routine approaching-deadline notices can be disabled, governance/overdue notices remain. Leadership Viewer can drill into reports but cannot mutate cases or decisions. Reports filter product/plant/period, distinguish unknown economics and require matching target metric/period/scope; submission cohort attainment uses the same filtered cases.
- FR15's broader replication workflow, richer scenario optimization, assisted discovery and operational integrations remain subsequent-release scope. Existing reuse links retain the concept relationship and never copy approvals. Priority and manual reasons support proportionate resource decisions; no automated optimizer is claimed.
